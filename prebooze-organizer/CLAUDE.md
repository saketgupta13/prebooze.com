# Prebooze Organizer (React Native / Expo)

Faithful port of the organizer web console (`prebooze-web/src/pages/organizer/`) to a native app for organizers only. Same backend (`prebooze-api` `/v1/organizer/*`), plus a push-token registration endpoint added for this app (`POST/DELETE /organizer/push-token`, live since 2026-09-17). Full spec lives in the original build prompt in conversation history — key points below.

**Round 4 (2026-09-15), 2 more pieces of feedback — wizard spacing + Scanner camera redesign:**
1. **Real bug found**: the wizard's step-pill row appeared to have a huge (~1000px) gap above the Basics-step form. Root cause was *not* padding — it was `EventWizardScreen`'s horizontal step-pill `ScrollView` having a `contentContainerStyle` but no `style` prop of its own. On Android, a `ScrollView` with no explicit `style` sitting as a *direct top-level sibling* of a `flex:1` `ScrollView` (the wizard's content area) can end up splitting the parent's remaining vertical space ~50/50 with that sibling instead of sizing to its own (small) pill content — confirmed via `uiautomator dump` bounds showing the pill row's `HorizontalScrollView` at 1032px tall against ~90px of actual pill content. Fixed with an explicit `style={{flexGrow:0, flexShrink:0}}` (`stepRowScroll` in `EventWizardScreen.tsx`) pinning it out of the flex distribution. This is a distinct bug from the Round 2 "stretched pill children" one (that was cross-axis stretching *inside* the row; this is the row's own main-axis height) — same general lesson though: an unstyled horizontal `ScrollView` next to a `flex:1` sibling on Android needs an explicit flex opinion, not just a `contentContainerStyle`. Checked `EventsScreen`'s similar `tabRow` `ScrollView` — safe, because it's nested *inside* another `ScrollView`'s content flow rather than a direct flex-column sibling of a `flex:1` one, so no fix needed there. Also tightened `stepRow`'s `paddingBottom` (`spacing.m`→`spacing.xs`) per the literal ask.
2. **Scanner's camera view rebuilt to match the "Prebooze App Concept" design artifact** — full-bleed `CameraView` (`camFull`) instead of a boxed camera under a separate header; a translucent overlay pill (`SearchableSelect` restyled via its new `fieldStyle`/`fieldTextStyle`/`chevronColor` props) for the event picker plus circular flash/flip icon buttons (`Zap`/`RefreshCw`) float over the top of the camera; an instructional text overlay; a corner-bracket scan frame (4 separate absolutely-positioned `View`s, not a bordered box) with an `Animated.Value`-driven sweep line looping 12%→86%→12%; and a bottom overlay with the manual-entry link + checked-in counter, kept visible even when camera permission isn't granted yet (previously that fallback state had no way back to manual entry — real UX gap, fixed by moving the manual-entry link outside the `permission?.granted` gate). `CameraBox` now accepts `facing`/`torch` props (wired to real toggle state) instead of hardcoding `facing="back"`, and its permission-denied fallback restyled to fill the same full-bleed container instead of a small square box.
   - **Real bug caught live**: the scan-line animation initially used `useNativeDriver: true`, which threw a visible in-app error toast — "Style property 'top' is not supported by native animated module" — because the animation drives `top` (a layout property, interpolated as a `'12%'`/`'86%'` string) and the native driver only supports `transform`/`opacity`. The startup log says so directly: "Metro is running in CI mode, reloads are disabled." Symptom: the app runs fine but shows stale content (e.g. an old date format, a placeholder screen), and `curl http://localhost:8081/index.bundle?platform=android&dev=true` either 200s with old code or (for a truly new file) returns a JSON `UnableToResolveError`. `CI=1` is still needed to avoid the interactive-prompt hang in this non-interactive shell — there's no way around restarting. **Standing rule: after *any* source edit, kill the Metro process and start a fresh `CI=1 npx expo start --dev-client --clear`, then verify via `curl .../index.bundle` that the new code is actually present (e.g. `grep` for a string unique to the change) *before* relaunching the app on-device** — this was missed repeatedly during the 2026-09-15 UI-feedback round and wasted real time chasing "why isn't my fix showing up" before the pattern was caught. Adding/changing a *native* module (e.g. `@react-native-community/datetimepicker`) additionally needs a real `npx expo run:android` rebuild, not just a Metro restart.
- **When screenshot-then-tap testing on the emulator, always compute tap coordinates from the most recent screenshot, taken immediately before the tap** — a `uiautomator dump` (or any screenshot) goes stale the instant the keyboard opens/closes or the ScrollView's position changes, and a tap computed from a stale dump can silently land on the wrong element with no error. Cost real time on 2026-09-14 (looked like "Next" button / step-pill taps weren't working, was actually just stale coordinates — confirmed once re-tested with a dump taken immediately before the tap). Also: the hardware/software back button (`adb shell input keyevent 4`) navigates the screen (`goBack()`) when no keyboard is actually focused, not just dismisses a keyboard — don't use it as a blind "close keyboard" action.
- **iOS Simulator left booted overnight silently ate the whole machine's CPU** (2026-09-14) — a `Prebooze Test` simulator from the prior day's Phase 0 work was still booted ~22 hours later; its background daemons (SpringBoard, diskimagesiod, dozens of others) had pushed the load average to 90-100+, starving an unrelated `expo run:android` build to near-zero progress even though it "looked stuck". A stuck-in-a-loop "System UI isn't responding" ANR dialog on the Android side was a downstream side-effect of the same CPU starvation and needed an `adb reboot` to clear (repeatedly dismissing it didn't converge).
- **A horizontal `ScrollView` sibling of a vertical content `ScrollView` can stretch its row children into tall capsules** — see the Phase 2 Round 2 entry above for the full root cause (flex row default `alignItems: 'stretch'` + Android `ScrollView` not reliably self-sizing as a flex sibling) and fix (`alignItems: 'flex-start'` on the row, not `flex: 1` on the other sibling). - **A second, distinct variant of the above**: an unstyled horizontal `ScrollView` (only a `contentContainerStyle`, no `style`) sitting as a direct top-level sibling of a `flex:1` `ScrollView` can end up sharing the parent's remaining vertical space ~50/50 with it on Android, ballooning to ~1000px tall instead of hugging its small content — this is the *row's own height*, not its children stretching (see Round 4 above). Worked around with a transparent 1x1 PNG manually placed at `android/app/src/main/res/drawable/splashscreen_logo.png`. A future clean prebuild will wipe this file and need the same fix redone (or check if the plugin has since added real no-image support upstream).
  - The original recropped `assets/splash-icon.png` (fixing its own real bug — the wordmark only filled 60%/12% of its 1200×1200 canvas, rendering as a barely-visible sliver once `expo-splash-screen`'s `imageWidth` scaling applied) is kept in the repo even though it's no longer referenced by the plugin config, in case a static native logo is ever wanted back.
- **A single `adb reboot` (not a full emulator restart) can leave the AVD's virtual network half-broken** — hit this 2026-09-18 right after using `adb reboot` to clear a "System UI isn't responding" ANR (itself caused by a real CPU-load spike from a concurrent native rebuild, same pattern as the black-screen-hang gotcha above): the *device* came back up and `adb devices` showed it connected, but the app's own Metro connection then failed with `ConnectException: Failed to connect to /10.0.2.2:8081` / `ENETUNREACH` — the emulator's virtual host-loopback interface itself was gone, not a stale `adb reverse` mapping (re-running `adb reverse tcp:8081 tcp:8081` did not help). Diagnostic: check `adb logcat -d | grep 8081` for the exact `ConnectException` rather than assuming it's a Metro/reverse issue. Fix: don't `adb reboot` a stuck AVD — fully kill it (`adb -s emulator-5554 emu kill`, then `kill -9 <qemu-system pid>` if it doesn't die within a few seconds — it can sit in uninterruptible sleep under load and ignore the graceful kill) and boot a fresh instance instead.

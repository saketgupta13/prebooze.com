# Prebooze — Backend Build Spec

The frontends (`prebooze-web`, `prebooze-admin`) are feature-complete on mock data and are **already wired for a real backend**:

- `prebooze-web/src/api/client.ts` — fetch wrapper (base URL, bearer token, typed errors). Offline when `VITE_API_URL` is empty.
- `prebooze-web/src/api/index.ts` — **one typed function per endpoint below**. Implement the server to this contract and the app goes live.
- `prebooze-web/src/lib/notify.ts` + `src/config/messaging.ts` — messaging templates + provider config; in backend mode each send POSTs `/notifications/send`.
- `prebooze-web/.env.example` — all environment configuration.

Recommended stack: Node (NestJS/Fastify) + Postgres + Redis (holds/OTP/queues) + Razorpay + AiSensy (WhatsApp, a Meta BSP) + Resend. All money in integer paise server-side.

**Status:** `prebooze-api/` (NestJS) is scaffolded and live locally — Prisma/Postgres + Redis. Working end-to-end and curl-verified:
- **Auth**: `/v1/auth/otp` + `/v1/auth/verify` + `/v1/me` (dev WhatsApp provider; real sends activate once `AISENSY_API_KEY` is set)
- **Identity & KYC**: guest auto-verify, role manual-submit, admin review queue — see that section for the policy and endpoints
- **Catalog** (Phase 2): all of Discovery below is live against seeded Postgres data — `prisma/seed.ts` ports `prebooze-web/src/data/mock.ts` 1:1 (same ids/slugs, so existing frontend links resolve unchanged); run `npm run seed` after any migration. Not yet wired into the frontend (still mock-mode by default) — flip `VITE_API_URL` when ready.
- **Bookings, holds, waitlist** (Phase 3): the full lifecycle is live and curl-verified — hold → quote (Razorpay order with the final amount) → create (atomic overselling guard, coupon, wallet credit, referral qualification, signed-QR ticket) → list → cancel (refund + inventory restore + FIFO waitlist offer) → check-in. `RazorpayService` follows the same dev-stub pattern as WhatsApp/KYC: unset `RAZORPAY_KEY_ID`/`SECRET` and the whole flow (orders, signature "verification", refunds) simulates instantly — no live gateway needed to test or develop against.
- **Wallet & payments, Referrals** (Phase 4): `GET /wallet`, Pay Methods CRUD + set-default (paying with a saved method at checkout also sets it default — wired into `POST /bookings`), `POST /me/auto-renew`, `GET /referrals` + `POST /referrals/claim` — all live and curl-verified, including the full loop: claim credits the referee's welcome bonus instantly, then the referee's first paid booking (already built in Phase 3) qualifies the referral and credits the referrer. `User.referralCode` is generated deterministically at signup (same `"PB" + base36(phone)` scheme as the frontend) so claim resolves a code to its owner without scanning every user.
- **Social** (Phase 5): follows/unfollows, followers, the (always-empty, honestly-so) follow-requests stub, attendance-visibility, interested/wishlist/venue-favourite toggles, organizer reviews — all live and curl-verified. Every follow is instant/accepted; there's no private-account approval flow in this product, see below.
- **Organizer console** (Phase 6): event create/edit (+ the minimal `/admin/events` approve/reject that closes the loop), attendees, coupons, payouts/withdraw, abandoned-cart recovery — all live and curl-verified. Approving an organizer's KYC now also provisions their `Organizer` catalog row (see Identity & KYC below) — without it they'd have no `Event.organizerId` to create events against.
- **Promoter console** (Phase 7): guest-list capture with all its fraud/quota guards, check-in, earnings, withdraw, team, subscription — all live and curl-verified. Approving a promoter's KYC now provisions their `Promoter` catalog row the same way Phase 6 did for organizers.
- **Venue partner** (Phase 8): onboard, listing GET/PATCH, events — all live and curl-verified. Unlike organizer/promoter, the `Venue` catalog row is created immediately at onboarding (unverified, already visible in the directory) rather than at admin-approval time — approval just flips the verified badge on.
- **Lineup**: turned out to need no new console endpoints (its dashboard/settings already ride on Catalog + `PATCH /me`) — just the same KYC-approval catalog-row-provisioning fix organizer/promoter/venue each needed, closed right after Phase 8. See "Lineup" below.
- **Featured, Support, Careers**: request/approval, help tickets, and job listings/applications — all live and curl-verified. Featured's write side (request + a minimal `/admin/featured` approve/reject) joins the read side that's been live since Phase 2. **Billing is now real** (2026-07-24) — see "Subscriptions" section below.
- **Admin API**: ✅ complete — all 13 slices live and curl-verified (see "Admin API" below for the full breakdown), including three rounds of sweeping prebooze-admin for missed pages after the user asked directly each time. Slice 13 closed the last two known gaps (full admin event CRUD, Lineups/BlogEditor fake image upload) plus 5 newly-found ones (manual customer onboarding, staff self-service profile, promoter subscription tiers, featured rates, manual/admin booking creation). No further gaps found — every route in `prebooze-admin/src/App.tsx` has a real backing endpoint. Next up per the user's sequencing: cron jobs.
- Not yet started: Cron jobs (weekly payouts, quota resets, auto-renew billing, featured expiry).

## Conventions
- Base URL `/v1`. JSON everywhere. Auth: `Authorization: Bearer <JWT>`; errors `{ code, message }` with proper HTTP status.
- Roles: `guest` (default), plus at most **one** elevated role per phone: `organizer | promoter | lineup | venue` (enforced at onboarding), `admin`, `staff`.
- All discovery endpoints are **city-scoped** via `?city=`.

## Data model (tables)
`users` (phone unique, name, username, email, city, dob, gender, bio, socials, interests[], id_verified, role, role_status: null|pending|approved|rejected, attendance_visibility, auto_renew, role-specific display fields), `otp_requests`, `kyc_submissions` (user_id, kind: guest|organizer|promoter|lineup|venue, status: pending|approved|rejected, payload json, documents json, auto_score, reviewed_by, review_note, reviewed_at), `people_follows` (follower_id, followee_key: person/org/promoter/venue/lineup prefixed), `follow_requests`, `events` (organizer_id, venue_id, category, sub_category, status: draft|pending|approved|rejected, date, duration, tags, rules, conditions, lineup[], seo, social_banners, promoter_config), `ticket_tiers` (event_id, name, price, qty, sold, includes[]), `venues`, `organizers`, `promoters` (slug, plan, status, kyc), `lineups`, `bookings` (user_id, event_id, tier summary, qty, amounts, status: confirmed|cancelled|refunded, promoter_ref, wallet_credit_used), `booking_guests`, `holds` (Redis, TTL 8 min), `waitlist_entries` (event_id, user_id, position, status waiting|offered), `carts` (abandoned-cart lifecycle), `wallet_txs` (user_id, type welcome|referral|refund|spend, amount), `pay_methods` (tokenized via Razorpay; never store PAN/CVV), `referrals` (code, referrer_id, referee_id, status joined|qualified), `promoter_guests` (event_id, promoter_slug, sub_promoter, name, phone, age, gender, arrived), `promoter_team`, `featured` (type, ref_id, city, billing, amount, status pending|active|rejected|expired), `featured_rates`, `sub_tiers`, `org_reviews`, `help_tickets`, `career_jobs`, `job_applications`, `career_teams`, `reels`, `locations` (country→state→city, enabled, top, icon), `notifications_outbox`, `admin_ledger`, `testimonials`, `faqs`, `policies`, `banners`, `blogs`, `menus`, `platform_settings` (singleton — booking fee, GST %).

## Endpoints (implement to match `src/api/index.ts`)

### Auth
- `POST /auth/otp` `{phone}` → `{requestId}` — send WhatsApp OTP (template `otp`), rate-limit per phone/IP.
- `POST /auth/verify` `{requestId, code}` → `{token, user, isNew}` — create user on first login (`attendance_visibility='off'`); if a pending referral code cookie/body is present, attribute + credit welcome.
- `GET /me` · `PATCH /me` — plain profile fields only (name, username, email, city, dob, gender, profession, languages, bio, socials, interests, attendance_visibility, auto_renew). `id_verified` and `role`/`role_status` **cannot** be set here — see below. `POST /auth/logout`.

### Identity & KYC
**Policy: guest verification is automatic; every elevated role (organizer/promoter/lineup/venue) is manual-only, reviewed by a human on the team.** This was a deliberate Phase-1 scope decision — automating the high-stakes roles before there's real fraud-pattern data to tune against risks false approvals of bad actors (fake organizers, scam venues) that cost real money and brand trust; guest verification is low-stakes (worst case, an unwarranted checkmark) and high-volume, so it's automated from day one. The data model (`role_status`, `kyc_submissions.kind`) is deliberately generic so any role can flip to automatic later without a schema change — see "Future" below.

- `POST /kyc/guest` `multipart: idDoc, selfie` — runs the pluggable KYC vendor check (OCR + face-match); dev/no-vendor-configured stub does basic file sanity checks. On pass: sets `id_verified=true`, `profile_pct=100` immediately, no human involved. On fail: rejected, user can retry. Always logs a `kyc_submissions` row (`kind='guest'`) for audit, even though it's fully automatic.
- `POST /kyc/role` `multipart: kind, payload (json: brand/username/gstin/bank details/etc), documents[]` — creates a `kyc_submissions` row (`status='pending'`) and stores the self-reported profile fields (orgBrand, promoterBrand, venueName, etc.) immediately for display, but **never** sets `role` or flips `role_status` to `approved` — that only happens via admin action below. Guards: one active application at a time (`role_status='pending'` blocks a second submission, for the same or a different role — one number, one role, enforced even mid-review); a `rejected` status does **not** block reapplying.
- `GET /kyc/me` — the caller's submission history (for showing "pending"/"rejected + reason" states client-side).
- `GET /admin/kyc?status=` · `POST /admin/kyc/:id/approve` · `POST /admin/kyc/:id/reject {reason}` — admin/staff only (see Admin API). Approve sets `role=kind`, `role_status='approved'` — this is the **only** code path that ever grants an elevated role. Reject sets `role_status='rejected'` with the reason stored, `role` stays null so the user can fix the issue and resubmit. Both should notify the applicant on WhatsApp. **As of Phase 6**: approving `kind='organizer'` also provisions a linked `Organizer` catalog row (slug-style id/username derived from `orgUsername`, collision-suffixed if taken) — `Event.organizerId` is a hard FK into `Organizer`, not `User`, so without this the newly-approved organizer would have nothing to create events against. **As of Phase 7**, `kind='promoter'` gets the same treatment — a linked `Promoter` row (separate slug-style `id` and `slug`, since `Promoter.slug` — not `id` — is the join key used everywhere: `event.promoterConfig.allowedPromoters`, `Booking.promoterRef`, `PromoterGuest.promoterSlug`). **As of Phase 8**, `kind='venue'` is different: the `Venue` row already exists by approval time (`VenueService.onboard` creates it, unverified, at submission — see "Venue partner" below), so approve() just flips `Venue.verified=true` rather than creating anything. **`kind='lineup'` gets the organizer/promoter treatment** (provisions a `Lineup` catalog row, slug-style `id`/`slug` derived from `lineupUsername`, `hue`/`emoji` picked deterministically) — added once it became clear Lineup has no dedicated console section below despite being one of the four elevated roles: `LineupDashboard.tsx` is fully derived from public Catalog data and `LineupSettings.tsx` saves profile edits through the plain `PATCH /me`, so this row-provisioning fix was the *only* real gap for the role to work end to end. See "Lineup" below.
- **Bank account verification (penny-drop)** for organizer/promoter payouts: deferred out of this manual-review flow — bundle it into the Wallet & payments / payout work instead, since it's an objective account-exists check, not a trust judgment, and doesn't need to block on human review.
- **Future**: once there's enough approved/rejected history to trust the vendor's accuracy on real traffic, organizer/promoter/lineup/venue can flip to auto-approve above a confidence threshold — same endpoints, just changing whether `/admin/kyc/:id/approve` fires automatically post-vendor-check instead of waiting on a human. No new endpoints needed.

### Discovery (public, city-scoped)
- `GET /events?city&cat&sub&search&sort` (approved only, featured-first), `GET /events/:slug`
- `GET /venues?city`, `GET /organizers?city`, `GET /promoters?city`, `GET /lineups?city`, `GET /people?city`
- `GET /featured?city` (active, in-window), `GET /categories` (tree + counts), `GET /cities` (event counts + top flags + icons from locations), `GET /search?q` (typed multi-entity suggestions), `GET /search/trending`

### Bookings, holds, waitlist — ✅ live (Phase 3), curl-verified end-to-end
- `POST /bookings/hold` `{eventId, qty:{tierId:n}}` → `{holdId, expiresAt}` — Redis-only, TTL 8 min (`HoldsService`). Validates tier existence + current availability at hold time as a soft check; the **hard** overselling guard is the atomic `tier.sold` update inside the booking transaction below, not the hold itself — two people can hold the same last ticket, only one will win at confirm time.
- `POST /bookings/quote` `{holdId, couponCode?, walletCredit?}` → `{subtotal, fee, discount, walletCreditUsed, total, razorpayOrderId?, razorpayKeyId?}` — call this before showing the Razorpay checkout widget; creates the Razorpay order with the **final** post-coupon/post-wallet-credit amount (Razorpay requires the order amount to match what's charged). Read-only — doesn't touch the hold or DB.
- `POST /bookings` `{holdId, mainGuest, whatsapp, guests?, couponCode?, walletCredit?, promoterRef?, razorpay?:{orderId,paymentId,signature}}` — re-derives pricing server-side (never trusts client amounts, same logic as `quote`), verifies the Razorpay signature, atomically guards + increments `sold` per tier, writes the booking (with a signed QR JWT, `tierBreakdown` for later inventory restoration), debits wallet, bumps coupon `used`, qualifies a pending referral on the buyer's first paid booking (credits the referrer, see Identity note below — this is real money, not KYC), sends `booking_confirmed`. `payMethodId` (saved cards/UPI) isn't wired yet — Pay Methods CRUD is still spec-only, see Wallet & payments below.
- `GET /bookings` · `POST /bookings/:id/cancel` `{refundTo: wallet|source}` — **behavior split as of the Admin API bookings/refunds/customers slice**, a deliberate decision (confirmed with the user, since it changes already-shipped Phase 3 behavior): `wallet` is unchanged — instant, sets `refunded`, restores `tier.sold`, instant `wallet_txs` credit, reverses the organizer's ledger credit, offers the freed spot FIFO to the next waitlist entry, all in the same request. `source` now only sets `refund_requested` and sends the new `refund_requested` template — **nothing else happens yet**: inventory, the organizer's ledger, and the waitlist all stay untouched until an admin actually approves (`POST /admin/bookings/:id/refund/approve`, see "Admin API"), so a decline can revert the booking to `confirmed` with nothing to unwind. This mirrors a common real-world pattern: low-risk in-house money (wallet credit) is self-service, real money leaving the business (Razorpay) needs a human.
- `POST /bookings/check-in` `{token}` — verifies the booking's signed QR JWT, rejects if not `confirmed` or already checked in, marks `checkedIn`+`checkedInAt`. One QR per booking (covers every guest on it), not per-guest — matches the ticket design.
- `POST /events/:id/waitlist` (auth required; dedupes per user via a DB unique constraint) · `GET /events/:id/waitlist` (**public** — the event page shows the waiting count to logged-out guests too).
- Abandoned-cart tracking: **as of Phase 6**, `POST /bookings/hold` also writes a durable `Cart` row (best-effort — never blocks checkout), and `POST /bookings` flips it to `completed`. See "Organizer" below for how recovery reads it. Still not yet built: promoter-commission ledger entries (`promoterRef` is stored on the booking but nothing reads it yet).

### Wallet & payments — ✅ live (Phase 4), curl-verified
- `GET /wallet` → `{balance, txs}`. Credits are spend-only; `balance` is just `sum(WalletTx.amount)`, no separate ledger table to keep in sync.
- `GET/POST/DELETE /pay-methods`, `POST /pay-methods/:id/default` — no CVV/CVV-token field exists anywhere in the input type, by design, not just convention — it never reaches the server. First saved method becomes default automatically; paying with a saved method at checkout (`POST /bookings {payMethodId}`) also sets it default.
- `POST /me/auto-renew` `{on}` — flips `User.autoRenew`. The cron that actually renews promoter subscriptions/featured monthly from the default method isn't built yet (see Cron / jobs) — this endpoint just records intent.

### Referrals — ✅ live (Phase 4), curl-verified end to end
- `GET /referrals` → `{code, referrals[]}` — `code` is `User.referralCode` (deterministic, set at signup). `POST /referrals/claim {code}` — requires auth (the referee must already have a user record from completing OTP login; the frontend stores the code pre-login via `/r/:code` and calls claim right after). Guards: self-referral rejected, one claim per phone ever (`Referral.refereeId` is `@unique`) — a `rejected`-style "already used" error, not silent success. Credits the referee's welcome bonus **immediately** on claim (`referral_welcome` wallet tx + WhatsApp); the referrer's reward (`referral_reward`) is credited later by `BookingsService.create` when the referee's first paid booking lands, qualifying the referral from `joined` → `qualified`. Amounts (`REFERRAL_REFEREE_WELCOME`, `REFERRAL_REFERRER_REWARD`, both ₹100 today) live in `src/referrals/referral.constants.ts`, shared with the bookings module so they can't drift — not yet admin-editable (`referral_rates` config table is future Admin API work).

### Social — ✅ live (Phase 5), curl-verified end-to-end
- `POST/DELETE /follows` `{key}` (prefixed keys: `person:`, `promoter:`, `lineup:`, venue/org ids) — every follow is instant/accepted (an upsert, so re-following is a no-op, not an error). **Design decision**: this product has no private-account approval flow — the frontend's followers/follow-requests split (built ahead of any real trigger for it, seeded with decorative ids that nothing ever populated) is served faithfully but honestly: `GET /me/follow-requests` always returns `[]` and `POST /me/follow-requests/:personId` is a harmless no-op, rather than being backed by a table nothing writes to. If private accounts become a real feature later, this is the seam to extend, not rebuild.
- `GET /me/followers` — who follows me, projected into the frontend's `Person` shape (`avatarHue` derived deterministically from the user id, matching the seeded catalog's cosmetic-only field). In practice this is empty today: there's no "discover other guests as a public profile" feature yet, so nobody can reach a `person:<userId>` follow target — this stays correct once that exists.
- `POST /me/attendance-visibility` `{v}` — gates who's-going visibility (`off | followers | public`), rejects anything else with 400.
- `POST /events/:id/interested` `{on}`, `POST /events/:id/wishlist` `{on}`, `POST /venues/:id/favourite` `{on}` — idempotent toggles (upsert on, delete on off).
- `GET /me/social` — **NEW, not in the original endpoint list**: closes a real gap — the toggles above have no accessor anywhere in `src/api/index.ts` or the `User` type, so a freshly logged-in client on a real backend would have no way to know what's already followed/interested/wishlisted/favourited. One bundled call (`{following, interested, wishlist, favouriteVenues}`) hydrates all of it at once, mirroring how `AppContext` currently boots the same state from localStorage together.
- `GET /organizers/:id/reviews` (public) — **NEW**, closes the read-side of the same gap: `POST /organizers/:id/reviews {rating, text}` was specced but nothing let a client fetch existing reviews (the mock kept them purely client-side, never fetched). Validates `rating` is an integer 1–5 and `text` is non-empty; the review's `date` is formatted server-side to match the mock's exact display format (`"21 Jul"`).
- Who's-going derivation (confirmed bookings + promoter-guest arrivals + interested, filtered by each attendee's visibility relative to the viewer): not built as a dedicated endpoint — nothing in `src/api/index.ts` calls for one today, and `goingCount`/`myStatus`/`friendsGoing` in `src/lib/social.ts` are all client-computed from data already fetched elsewhere (event tiers, `GET /bookings`, the new `GET /me/social`). Revisit if/when the frontend needs "friends going" social proof on a *real* social graph instead of the seeded `Person.follows` array.

### Promoter — ✅ live (Phase 7), curl-verified end-to-end
- `GET /promoter/promotions` — approved events where `promoterConfig.enabled` and the caller's `Promoter.slug` is in `allowedPromoters`. `GET /promoter/events/:id/guests` — that event's guest list, scoped to the caller's own slug.
- `POST /p/:eventSlug/:promoterSlug` — **public**, no auth, reached via the promoter's affiliate link. Guards run in the same order as the frontend's mock (`GuestLanding.tsx`), including its quirk: **cap/quota are checked before the returning-guest lookup**, so once a list is full even someone already on it won't get their existing pass back through this endpoint — kept intentionally, since matching mock parity was the goal, not fixing a UX edge case nobody asked about. Guards: event must be `approved`, promoter must be allow-listed, age vs. the event's `ageLimit`, list `cap`, the promoter's monthly plan quota (`SUB_TIERS` mirrored server-side: free 25 / starter 150 / pro 500 / elite unlimited), one pass per phone per event (returns the existing `PromoterGuest` row, not an error), then a 3+ no-show block (past lists this phone joined, cutoff elapsed, never arrived — checked across *all* events, not just this one). Sends a new `guest_pass` WhatsApp template with the pass link — not in the original template list, since the mock version of this flow never actually sent anything (same reasoning as Phase 6's `cart_reminder`).
- `POST /promoter/guests/:id/check-in` — ownership-guarded to the promoter who owns the guest's `promoterSlug` **or** the organizer who owns the guest's event ("scanner" scope from the original endpoint list isn't implemented — there's no such role in the data model yet, only `organizer/promoter/lineup/venue`). **Deliberately idempotent one-way**, not the mock's toggle-based "undo": the real endpoint contract (`checkInGuest(id)` in `src/api/index.ts`) takes no rotation token or on/off flag, and a public-facing gate action shouldn't be reversible by tapping twice. The QR's 5-second-rotating seed is purely a client-side screenshot deterrent — there's no token param for the server to validate, contrary to this section's original spec note.
- `GET /promoter/earnings` → `{perHead, commission, withdrawn}` — computed live from `PromoterGuest.arrived` (× each event's `perHeadAmount`) and confirmed `Booking`s with `promoterRef` set (× an 8% commission rate, mirroring `promoterEarnings.ts`), not from a stored ledger — everything needed is already reconstructible from those two tables. `POST /promoter/withdraw {amount}` — minimum ₹500, capped at `perHead + commission - withdrawn`, backed by the new `PromoterWithdrawal` table.
- `GET/POST /promoter/team` — sub-promoter handles scoped to the caller's own `Promoter`; adding a duplicate handle silently returns the existing row (matches the mock's no-op-on-duplicate behavior, not an error).
- `POST /promoter/subscription {planId}` — validates against the known plan ids and records the choice. **No billing is wired up** — same documented gap as Featured's payment flow, not an oversight.

### Organizer — ✅ live (Phase 6), curl-verified end-to-end
- `GET/POST /organizer/events` — create/edit, resolving `organizerId` server-side from the caller's linked `Organizer` row (never trusts a client-supplied one). `status` is client-controllable only between `draft`/`pending` — `approved`/`rejected` are review outcomes and can only be set via the admin endpoints below, even on an edit of an already-approved event (any edit resubmits to `pending`, matching the frontend's save-draft-vs-submit split). **An edit is a merge onto the existing row**, not a wholesale replace — omitting a field (or `tiers`) leaves it as-is rather than blanking it; this was a real bug caught while curl-verifying (a status-only resubmit was wiping description/category/tiers) and fixed before shipping. Ticket tiers are diffed: existing tiers matched by id are updated in place, new ones (no id, or an unrecognized one) are created fresh, and any tier removed from the payload is deleted **unless it already has sales**, which throws instead of silently orphaning sold tickets' `tierBreakdown` references.
- `GET /organizer/events/:id/attendees` — flattens each of the event's bookings' `guests[]` into one row per guest (name, whatsapp, checked-in, which booking/tier), ownership-guarded.
- `GET/POST /organizer/coupons` — scoped to the caller's own `Organizer.id`. Creating a coupon with `eventScope` set to something other than `'all'` validates that the organizer actually has an event with that title. **Bug fixed while building this**: `Coupon.organizerId` didn't exist before Phase 6, so an organizer's own coupon with `eventScope: 'all'` would apply to *any* event platform-wide, not just theirs — `BookingsService.priceHold` now checks `coupon.organizerId` against the event's organizer independently of `eventScope`, closing the leak (verified live with a deliberately cross-organizer coupon).
- `GET /organizer/payouts` → `{balance, ledger}`, `POST /organizer/withdraw {amount}` (rejects non-positive or over-balance amounts, sends `organizer_payout`) — backed by the new `OrganizerLedgerTx` table, credited the booking `subtotal` (not the per-ticket fee, which is platform revenue) when a booking on the organizer's event is confirmed, debited by the same amount on cancellation/refund, and debited on withdrawal. **No commission/take-rate is modeled yet** — organizers are credited the full ticket subtotal; this is a deliberate placeholder (nothing in the spec defines a take-rate) documented here so it isn't mistaken for an oversight when a real commission model is designed later.
- `GET /organizer/carts` (abandoned for their events) · `POST /organizer/carts/:id/remind` (`cart_reminder` WhatsApp template — new, not in the original template list, see Support/careers/notifications below). No cron exists yet, so abandonment is evaluated **lazily at read time**: a `Cart` row (written by `POST /bookings/hold`, see "Bookings, holds, waitlist" above) counts as abandoned if it's the *most recent* hold for that user+event, still `active`, and older than the hold TTL (8 min) — deduped so an earlier abandoned attempt doesn't linger in the list after the shopper came back and actually completed a later one.
- `POST /admin/events/:id/approve` · `POST /admin/events/:id/reject {reason}` · `GET /admin/events?status=` — **new, not in the original endpoint list**: closes the loop opened by organizer-created events, which would otherwise have no way to ever leave `pending`. Deliberately minimal — a full events-review console with everything `prebooze-admin` needs is separate Admin API work, not duplicated here. Gated on real staff auth + the `"Events & approvals"` permission as of the Admin API auth slice (previously the placeholder `x-admin-secret` header — see "Admin API").

### Venue partner — ✅ live (Phase 8), curl-verified end-to-end
- `POST /venue/onboard` — creates the `Venue` catalog row **immediately** (id/slug derived from the name, collision-suffixed if taken; `verified: false`) so it shows up in the city directory and is pickable by organizers creating events right away, *and* a `pending` `KycSubmission` (`kind='venue'`), *and* sets `User.venueName/venueId/roleStatus='pending'` — all in one call. This is the one meaningful way it differs from organizer/promoter onboarding, where nothing in the catalog exists until an admin approves (see Identity & KYC above for how `approve()` handles each kind differently as a result). **Auth + permission matrix — ✅ live, curl-verified end-to-end.** `prebooze-admin` had *no* typed API contract at all before this (unlike `prebooze-web`'s `src/api/index.ts`) — its whole app is still mock/localStorage, including a login screen that accepts any email/password combo and never checks anything. This slice replaces the placeholder `x-admin-secret` header that `/admin/kyc`, `/admin/events`, and `/admin/featured` used until now with real accounts, built by reading `prebooze-admin/src/store/AdminContext.tsx` directly since there was no contract file to build against.

- **Staff model**: `Staff` (email/passwordHash/roleName) + `StaffRole` (name → `{ [module]: {view, edit, approve} }`, matching `RoleMatrix` exactly). Password hashing uses Node's built-in `scrypt`, not a new dependency (`bcrypt`/`argon2`) — consistent with how lean the rest of the auth stack already is. `PERM_MODULES` and the six seeded roles (Owner/Manager/Finance/Content/Support/"Scanner only") are ported verbatim from `prebooze-admin/src/store/data.ts` into `prisma/seed.ts`, including their exact per-cell permissions.
- **A real design finding, not a guess**: `Session.role` (`'admin'|'staff'`) in the mock — the tab you click on the login screen — is purely cosmetic; grep confirms it's used in exactly one place (`AdminLayout.tsx`, to render a "STAFF"/"ADMIN" badge) and never gates any actual permission check anywhere in `AdminContext.tsx`. The real permission unit is the role *name* (`StaffMember.role`, looked up in `RoleMatrix`). `POST /admin/auth/login` reflects this: it takes only `{email, password}` and deliberately ignores which tab the client submitted — real access comes from the staff's assigned `roleName`, resolved server-side.
- `POST /admin/auth/login {email, password}` → `{token, staff: {id, name, email, roleName, permissions, city}}`. `GET /admin/auth/me` (any authenticated staff). Staff and guest JWTs share the same signing secret for simplicity but are never interchangeable: `StaffAuthGuard` requires `staffId`+`roleName` in the payload, and the guest `JwtAuthGuard` was hardened to require `sub`+`phone` — a token issued for one principal type is rejected outright by the other's guard, not silently misread (verified live both directions).
- `GET/POST/PATCH/DELETE /admin/staff` and `/admin/roles` — **Owner-only**, not part of the delegatable permission matrix at all (`PERM_MODULES` has no "Staff & roles" entry — letting a role edit the matrix that grants its own permissions would be a privilege-escalation hole, so it's hardcoded to `roleName === 'Owner'` instead of a matrix cell). Creating staff has no invite-email flow yet (`RESEND_API_KEY` isn't wired up) — returns a one-time random temp password in the response for the Owner to share out-of-band. Guards ported from the mock exactly: the `Owner` role itself can never be removed, and a role still assigned to any staff can't be removed either (`"Reassign members using ... first"`). A dev-only bootstrap Owner account is seeded (`owner@prebooze.com` — see `prisma/seed.ts` for the password; rotate before any real deployment) since creating staff requires an already-logged-in Owner.
- `/admin/kyc`, `/admin/events`, `/admin/featured` all swapped from the placeholder secret onto `StaffAuthGuard` + a `@RequirePermission(module, level)` per route. Mapping existing admin actions onto `PERM_MODULES` required judgment calls documented here since the mock's matrix predates half of what it now gates: KYC approvals → `"Customers & organizers"` (closest fit — granting a role is fundamentally a trust decision about a business account), events → `"Events & approvals"` (clean fit), featured → `"Content (banners / blogs / pages)"` (closest fit — promotional placement, not literally event or customer data). `reviewedBy` on `KycSubmission` now records the approving staff's real email instead of a free-text `x-admin-user` header.

### Featured billing — ✅ real (2026-07-24)
Previously `FeaturedService.request()` only ever recorded a pending request + an invoice nobody was charged for — the exact same "documented gap" Promoter subscription used to have. Now: `request()` creates a real Razorpay order for `amount + GST` (`Featured.razorpayOrderId`), returned to the caller as `{...row, razorpayOrder: {orderId, amount, keyId}}` for the frontend to complete checkout with. New `POST /featured/:id/confirm-payment {paymentId, signature}` re-checks ownership (Featured has no `userId` column, so this re-runs the same `resolveTarget` ownership check `request()` used) and verifies the signature via `RazorpayService.verifyPaymentSignature`; only then is `Featured.paid` set `true`. `adminApprove()` now throws if `!paid` — admin can no longer approve (make live) a request nobody actually paid for. **Verified for real, live keys**: real order created (`order_THGngBKwnTxaVV`, ₹3,539 incl. ## Real QR — ✅ live
Every booking gets a signed `qrToken` at creation: `JWT { bookingId }`, 30-day expiry, one per booking (covers every guest on it — matches the ticket design, not per-guest). `POST /bookings/check-in {token}` verifies the signature, confirms the booking is `confirmed` and not already checked in, then marks it — and as of the Admin API's Live Monitor slice, writes a `CheckInLog` row on every branch (success or rejection), which is what backs the admin Live Monitor's gate feed and rejected-QR count. Promoter guest-pass rotating tokens (5 s window) — not built yet, that's promoter console write-side work.

## Cron / jobs — `src/admin/cron.service.ts`, `@nestjs/schedule`
- **Auto payout** (`autoPayoutTick`, daily 08:00): runs the same batch-payout logic as the manual "Run batch" admin button, only when today matches Settings' configured payout day and `autoPayout` is on.
- **Weekly summary email** (`weeklySummaryTick`, Mondays 08:00): real revenue/bookings/payouts-due numbers to every Owner-role staffer, gated on Settings' `weeklyEmail` toggle.
- **Featured expiry** (`featuredExpiryTick`, hourly): flips `Featured.status` `active`→`expired` once `expiresAt` passes — the public catalog already hid expired ones via a live date filter regardless of `status`, but admin's own Featured list read `status` directly and showed lapsed placements as "active" forever until this existed.
- **Featured expiring-soon reminder** (`featuredExpiringSoonTick`, daily 09:00, new 2026-07-24): proactively emails the owner 3 days before expiry, once per placement — see "Featured expiry reminders" above for the full detail and the pre-existing manual `POST /admin/featured/:id/remind` it complements.
- **Monthly promoter quota reset**: turned out to not be needed — `PromoterService.planQuota()`'s guest-add check counts the *current calendar month's* guests live rather than decrementing a stored counter, so it already self-resets every month with no cron required.
- **Wallet auto-renew** (auto top-up) and **staff WhatsApp number capture** (`Staff.phone`, captured on `POST /admin/staff`, wired into refund-request/KYC-submission/payout-failure alerts via `StaffAlertsService`) — see their own sections; wallet auto-renew stays reported-only (user declined, pending a real Razorpay e-mandate design for it specifically, separate from the Subscriptions system above).
- Hold expiry sweep, abandoned-cart marker, waitlist FIFO offers with 15-min claim windows — unchanged, pre-existing.
